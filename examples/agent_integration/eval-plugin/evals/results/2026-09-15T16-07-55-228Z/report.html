Fixed. Here's what happened and where it sat.

## The disagreement

The second commit, `059c0ab "accounts: simplify creation"`, gutted the write in `ecommerce_backend/domain.py:88`:

```python
def create_account(self, account_id: str) -> OperationResult:
    with self._conn:
        pass  # a change from an earlier commit
    return OperationResult(201, {"account": account_id})
```

The endpoint still answered `201 {"account": ...}`, so the response contract looked intact — but no row ever landed in `accounts`. Every downstream guard that reads account existence (`add_cart_item`, `checkout`, both via `_account_exists`) then failed with `404 account_not_found` for an account the client had just been told was created. All three service roles (`monolith`, `database`, `gateway` at `service.py:152,205,248`) funnel into this one method, so it was a single break with a whole-surface blast radius.

## The repair

Restored the insert:

```python
self._conn.execute("insert or ignore into accounts(account_id) values (?)", (account_id,))
```

`insert or ignore` is what the model wants for the duplicate case too. Verified by exercising the store directly: create → `accounts: ['acct-1']`; re-create → still `201`, still one row (matches `SubmitDuplicateCreateAccount`); then `add_cart_item` 202, `checkout` 202 with the order in the outbox, `process_outbox` 200 draining it to `ready_to_ship`, re-checkout 200 idempotent, unknown account 404. The model itself is untouched.

## Which action it sat under

`Internal.CreateAccount` — surfaced at the outer view as `External.SubmitCreateAccount`, which conjoins it (`External.tla:44`). The adapters confirm the binding is exactly one call: `CreateAccountInternalAdapter` → `store.create_account`, `CreateAccountHttpAdapter` → `POST /accounts`.

## What in the model would have caught it

The action's next-state relation, not an invariant — worth being precise about, because the invariants would have stayed green:

- **`Internal.tla:18` — `accounts' = accounts \cup {a}`.** This is the whole catch. The model has no step in which a `201`-returning create leaves `accounts` unchanged: `CreateAccount` is guarded by `a \notin accounts` and *must* grow the set; the only other 201 is `SubmitDuplicateCreateAccount`, guarded by `a \in accounts` (`External.tla:51`) and explicitly `UNCHANGED InternalVars`. The broken program produced a step matching neither — 201 with an empty set — so a conformance check of the post-state against that action fails on the very first case.
- **The downstream enabling condition, `AddCartItem`'s `a \in accounts` (`Internal.tla:23`).** In the model, a successful create *enables* `AddCartItem` for that account. In the program it no longer did. Any generated two-step trace `SubmitCreateAccount` → `SubmitAddCartItem` — exactly the `Scenario_CheckoutHappyPath` slice declared in `spec_manifest.yaml:29` — diverges at step two: model says 202, program said 404.

By contrast, `InternalInvariant` (`Internal.tla:53`) only constrains `outbox ⊆ Orders` and that queued orders are `accepted`, and `ExternalInvariant` adds only service-health and route well-formedness. All of those hold happily in a world where no account is ever created. The state-based safety properties were blind here; the step relation of the action was not.

The spec is in place under `specs/program_model/` and checks clean.

**What I built.** `shortlink.py` is one `Shortener` with three dicts and four public methods, so the model is one action per method and one guard per `raise ShortlinkError`. A refused call is a *disabled* action, not a transition — the program raises and changes nothing. `Blank` does double duty for "key absent from the dict" and "caller passed an empty string", which is faithful: `if not slug` and the dict lookup are testing the same thing.

Three rules turned out not to be invariants at all — they're false of no single state, so they're `PROPERTIES` over the next-state relation: `OwnershipNeverTransfersInPlace` (the release-then-re-reserve rule), `OnlyTheOwnerReleases`, and `ClaimGrantsToTheReservationHolder`. The last two are the authorization rules; a slug released by a stranger lands in a state indistinguishable from one the owner released, so only the transition tells them apart.

**Results:** `Internal.cfg` — 169 distinct states, depth 6, no error. `HandoffWitness.cfg` — the expected violation, printing ana reserves → claims → releases → bo reserves → claims. Repo tests: 9 passed, 2 skipped (the four fixture tests green).

Three things worth flagging:

- **The scaffold shipped a failing test.** `test_program_model_onboarding.py` read `External.tla` and `testgraph_bindings.yml` unconditionally, contradicting its own docstring and the four-file minimum — it fails on every minimum baseline. I made those two checks skip when the optional layer is absent.
- **The CLI is broken under `python3`.** `bin/tla-spec-dev` execs `python3`, which is 3.9.6 here, and `scripts/onboard_program_model.py:1138` uses a PEP 701 nested-quote f-string: every subcommand dies with `SyntaxError`. I ran the checkout's script directly under `/opt/homebrew/bin/python3.14`.
- **TLC needed two sandbox workarounds.** `/usr/bin/java` is the Xcode stub; and `tlc2.tool.fp.FPSet extends java.rmi.server.UnicastRemoteObject`, so every run binds an anonymous RMI port — which this sandbox forbids (`ExportException: Listen failed on port: 0`). I ran TLC through a small launcher installing an `RMISocketFactory` whose server socket never binds, plus `-Djava.io.tmpdir=$TMPDIR`. Both are recorded in `results/negative_controls.md`. I tried to save these toolchain notes to memory but that directory is denied for writing in this session.

The module's action list, verbatim from `specs/program_model/Internal.tla`:

```tla
InternalNext ==
  \/ \E s \in SlugArgs, o \in OwnerArgs : Reserve(s, o)
  \/ \E s \in SlugArgs, o \in Owners, t \in TargetArgs : Claim(s, o, t)
  \/ \E s \in SlugArgs, o \in Owners : Release(s, o)
  \/ \E s \in SlugArgs : Resolve(s)
```

**What would have caught me if I'd got it wrong.** Not the passing TLC run — a spec with no actions passes too. I ran seven mutations against the unchanged config (`results/negative_controls.md`): dropping the already-live guard from `Reserve`, the stranger guard from `Claim`, and the ownership guard from `Release` each fire a specific named failure, as do a `Claim` that leaves the reservation behind, a `Claim` that writes `links` but not `slugOwners`, and an added in-place `Transfer`.

The one that matters is row 7. Deleting `Release` entirely — the documented way to under-model this program — leaves `Internal.cfg` reporting **no error**, because every invariant and property is then vacuously true. Nothing in the main config notices. That is why `HandoffWitness.tla` exists: it runs the same next-state relation with one history variable and asserts a deliberately false invariant, so it must report a violation. With `Release` deleted it goes quiet. A green witness run is the bug report, and that specific gap is what would have caught me.
